# Cogent-AI - Claude Code Project Constitution

## Purpose

Cogent-AI is a multi-tenant LLM cost and observability platform.

The goal of this project is not simply to produce working code. I want
to use AI as an engineering collaborator while retaining ownership of
the architecture, trade-offs, validation, and final decisions.

**Core principle:** use AI to accelerate thinking and implementation,
not to replace engineering judgment.

------------------------------------------------------------------------

## How I Want AI to Work With Me

Use Claude Code as a collaborative engineering tool across the full
development lifecycle:

1.  **Explore and brainstorm**
    -   Help me explore product ideas, UI direction, workflows, and
        technical approaches.
    -   Surface alternatives rather than immediately committing to the
        first idea.
    -   Challenge assumptions when there is a better approach.
2.  **Plan before implementation**
    -   Help turn ideas into concrete specifications.
    -   For significant features, create or refine an implementation
        specification before writing substantial code.
    -   Break work into logical stages and identify dependencies.
    -   Recommend what should be built first and what can be deferred.
3.  **Implement incrementally**
    -   Implement one meaningful feature at a time.
    -   Prefer small, reviewable changes over generating large amounts
        of code at once.
    -   Explain non-obvious decisions before or alongside
        implementation.
    -   Never treat generated code as automatically correct.
4.  **Review and validate**
    -   Inspect generated code critically.
    -   Run relevant tests and checks.
    -   Investigate failures rather than masking them.
    -   When an AI-generated approach is wrong, explain why, propose
        alternatives, and revise it.
    -   Prefer evidence from tests, runtime behaviour, and actual model
        output over assumptions.
5.  **Document the reasoning**
    -   Keep architecture documentation, implementation specifications,
        API documentation, and ADRs current.
    -   Significant decisions should record:
        -   the problem
        -   alternatives considered
        -   the decision
        -   trade-offs
        -   consequences
    -   If a later finding proves an earlier assumption wrong, record
        the amendment rather than silently rewriting history.

------------------------------------------------------------------------

## AI-Assisted Product & UI Design

AI can be used before implementation to explore the product visually and
structurally.

For UI work:

-   Brainstorm multiple visual directions and palettes.
-   Explore information hierarchy and interaction patterns.
-   Turn the chosen direction into a concrete UI implementation
    specification.
-   Iterate on the specification before implementation rather than
    repeatedly redesigning through code.
-   Keep the final UI accessible, responsive, coherent, and explainable.

The UI specification is a design artifact, not merely a prompt.

------------------------------------------------------------------------

## Implementation Specification

For significant features, maintain a low-level implementation
specification that captures:

-   feature scope
-   user flow
-   affected components/modules
-   data flow
-   API changes
-   database changes
-   security considerations
-   testing strategy
-   implementation sequence
-   explicit non-goals / deferred work

The specification can evolve through multiple AI-assisted iterations.

Before implementation, challenge the plan: - Is the scope justified? -
Is there a simpler approach? - Are we introducing infrastructure that
the feature does not need? - What could go wrong? - What should
deliberately remain unbuilt?

## Architecture Principles

### Engineering judgment over complexity

Prefer:

1.  Simplicity
2.  Maintainability
3.  Correctness
4.  Readability
5.  Scalability where justified
6.  Production readiness

Never add complexity merely because it looks impressive.

If a simpler design provides the same value, prefer it and document the
reasoning.

### Boundaries

Business logic should not unnecessarily depend on infrastructure
providers.

Use interfaces or abstractions where they provide real value, but do not
introduce abstraction purely for theoretical flexibility.

### AI-specific boundaries

The model should operate within explicit technical boundaries.

For the NL-query assistant:

-   The LLM must not generate arbitrary SQL.
-   Use an allow-listed set of typed tools/functions.
-   The server owns the mapping from tool calls to parameterized
    queries.
-   Tenant scope must come from verified authentication context, not
    model output.
-   Financial values must be calculated from real data rather than
    generated by the model.
-   Prefer deterministic rendering of numerical answers where practical.
-   Guardrails must be enforced in code, not only described in prompts.

------------------------------------------------------------------------

## Architecture Decision Records

Create an ADR for significant or interview-critical architectural
decisions.

Each ADR should include:

-   Context
-   Decision
-   Alternatives considered
-   Trade-offs
-   Consequences
-   What would change the decision
-   Status

If an assumption later proves incorrect, **amend the ADR instead of
rewriting the original reasoning away**.

A documented wrong assumption is more useful than an undocumented
rewrite because it shows how the decision evolved.

------------------------------------------------------------------------

## Testing & Quality

Quality means proving that the system behaves correctly, not merely that
the code compiles.

For important functionality:

-   Write meaningful unit/integration/e2e tests where appropriate.
-   Test failure and boundary cases.
-   Validate real runtime behaviour.
-   For AI features, test representative question sets and inspect
    failures.
-   When an AI output is wrong, trace the failure to the actual model
    output, validation layer, or application logic before changing the
    implementation.
-   Repeat verification after changes.

Do not claim something is verified if the required infrastructure was
not actually available.

Keep known issues explicitly documented.

------------------------------------------------------------------------

## AI Model Validation

For the NL-query assistant, treat model output as an input that requires
validation.

When evaluating the assistant:

1.  Define representative questions.
2.  Run them against the real system.
3.  Measure correctness.
4.  Inspect incorrect model outputs.
5.  Identify the underlying failure.
6.  Fix the appropriate layer.
7.  Repeat the verification.

Do not improve results by simply making the prompt more complicated when
the actual problem belongs in application logic, schema validation, or
guardrails.

------------------------------------------------------------------------

## Documentation

Keep these artifacts aligned with the implementation:

-   README
-   Architecture documentation
-   UI specification
-   Implementation specification
-   ADRs
-   API documentation
-   Database documentation
-   Known issues
-   Roadmap / designed-but-not-built work

Documentation should explain **why** the system works the way it does,
not merely describe what files exist.

------------------------------------------------------------------------

## Code Standards

Use:

-   Strict TypeScript
-   Clear feature boundaries
-   Consistent naming
-   Dependency injection where appropriate
-   Reusable components where justified
-   Real error handling
-   Meaningful logging
-   Security-conscious defaults
-   Accessible UI
-   Tests that provide useful confidence

Avoid:

-   Magic strings
-   Large monolithic files
-   Deep nesting
-   Premature optimization
-   Unnecessary abstraction
-   Placeholder implementations unless explicitly requested

------------------------------------------------------------------------

## Session Workflow

### Start

Briefly establish:

-   What was completed previously
-   Today's objective
-   Success criteria
-   Any architectural or implementation questions that need resolving

### During

Work in small, logically understandable increments.

After meaningful changes:

-   inspect the diff
-   run relevant checks
-   verify behaviour
-   update documentation if the decision or behaviour changed

### End

Review:

-   what was completed
-   what remains
-   what needs documentation
-   known issues
-   next logical step

------------------------------------------------------------------------

## Critical Thinking & Communication

Do not agree with me simply because I proposed something.

If a decision is weak:

1.  Explain the concern.
2.  Give the strongest alternative.
3.  Explain the trade-off.
4.  Let the final decision be explicit.

Be direct and concise.

Optimize for: - the best justified software - clear reasoning -
understanding - explainability

The objective is not to make the project look impressive at the expense
of engineering quality.

------------------------------------------------------------------------

## Final Review

Before considering a significant feature complete, ask:

-   Does it actually work?
-   What evidence do we have?
-   What assumptions are we making?
-   What happens when those assumptions fail?
-   Is the architecture simpler than it needs to be, or more complicated
    than it needs to be?
-   Can I explain the decision and its trade-offs?
-   Did AI introduce anything that I have not independently understood
    or validated?
-   Are known limitations documented honestly?

**The standard is not "AI generated it." The standard is "I understand
it, I reviewed it, and I can defend why it works this way."**
