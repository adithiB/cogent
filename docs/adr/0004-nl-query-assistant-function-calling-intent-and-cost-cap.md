## Context

The Statement, its data layer, and its scope discipline are built (ADR-0001, ADR-0002). What remains is the feature the whole product exists to demonstrate: an LLM that turns "what did checkout-service spend on GPT-4o last week?" into an answer over one org's usage data, safely.

ADR-0003 named the three failure modes an LLM over multi-tenant billing data has to close — runaway cost, cross-tenant leakage, out-of-scope hallucination — and asserted the shape of the closure. ADR-0002 then built the read layer that closure binds to. This ADR is where the assertion becomes a running system, and it answers four questions ADR-0003 left as shape rather than mechanism:

1. **Is the allow-list actually unforgeable, by construction, given the code that exists?** (Decision 1.)
2. **How is `intent: 'point' | 'slice'` actually set** — by the function, by the model's arguments, or both? (Decision 2.)
3. **What does "hard per-query $0.02 cap" actually enforce** — before spend or after? "Query paused" or "answer then apologize"? (Decision 3 — the centerpiece.)
4. **How does the system know a query is out of scope without paying an LLM call to find out?** (Decision 4.)

**What exists today (verified in-repo, not recalled).** `UsageEventsRepository` exposes exactly `getSpend`, `getRequestVolume`, `getLatency`, `getErrorRate` (each `(scope, args: MetricArgs) → MetricResult`) and `getStatement` (`(scope, args) → { rows, totals }`), plus the write path `insertEvent`. Every read composes its `WHERE` through `orgScope(usageEvents.orgId, scope)` — the one predicate helper — plus `gte/lt` on the window and an optional `eq` on a filter dimension. Every SQL fragment is a hand-written parameterized Drizzle expression; `metricArgsSchema` is `z…strict()` with no `orgId` field. Nothing below invents a data path; it wires an LLM to this one.

## Decision 1 — The allow-list *is* the function-calling tool set. Verified unforgeable by construction, not by post-hoc validation.

**The claim, stated precisely, then checked against code.** An LLM doing Anthropic tool-use against exactly these functions cannot construct an arbitrary query — not because the server validates the model's output against a schema after the fact, but because the tool-calling interface only exposes these call shapes. There is no code path in the design below where model output becomes a raw SQL fragment, a free-form filter, or anything that reaches the database except as an argument to one of the named functions, parsed by its existing Zod schema, with `scope` supplied by the server.

**The binding.** The assistant exposes five tool definitions to the model:

- Four data tools — `getSpend`, `getRequestVolume`, `getLatency`, `getErrorRate` — whose `input_schema` is the JSON-Schema projection of the **existing** `metricArgsSchema` (`window`, optional `groupBy ∈ {project,team,model,time}`, optional `filter ∈ {dimension ∈ {project,team,model}, value: string}`), declared `strict: true` so `input` validates the schema exactly with `additionalProperties: false`.
- One control tool — `report_out_of_scope` (Decision 4) — with `{ reason: string, suggested_rephrasings: string[] }`.

`getStatement` is **not** an LLM tool — it is the deterministic render/re-scope path the UI drives (Decision 2).

The dispatch, step by step, is where "by construction" has to hold:

1. The model returns one `tool_use` block: `{ name, input }`. (One, because `tool_choice: "any"` forces exactly one tool and no prose — Decision 3 and 4 rely on this.)
2. The server matches `name` against a **hardcoded map of exactly these five names**. No match → structurally impossible under `tool_choice: "any"` with this tool set, but treated as out-of-scope, no DB call.
3. `input` is parsed by the corresponding **existing** Zod schema (`metricArgsSchema`). Parse failure → rejected, no DB call.
4. The server calls `repo[name](scope, parsedArgs)` where `scope` is the `TenantScope` from the verified credential (ADR-0001), never anything on `input`.

**The proof obligation the prompt set — "is there any path where model output becomes SQL?" — discharged.** Walk what the model can influence:
- **The function** — chosen from a closed set of four; a sixth capability does not exist to be named.
- **`groupBy` and `filter.dimension`** — `z.enum` values; the model cannot supply an arbitrary column, and `dimensionColumn()` (verified in `usage-events.repository.ts:29`) switches over the enum to a fixed SQL fragment.
- **The window** — two dates; used in `gte`/`lt` bound parameters.
- **`filter.value`** — the one place model-controlled *free text* reaches the query. It reaches it as a **bound parameter** (`eq(dimensionColumn(...), args.filter.value)`, `usage-events.repository.ts:87`), never concatenated into SQL text. It is data (a project/team/model name to match), not code. This is the honest edge worth naming out loud in an interview: there is exactly one free-text argument the model controls, and it is parameterized, so it cannot alter query structure — the difference between "the model picks which rows" and "the model writes the query" is the whole ADR-0003 thesis, and it holds here at the one point it could have leaked.

**Cross-tenant, restated as a construction fact.** No tool's `input_schema` contains `orgId` (because `metricArgsSchema` is `.strict()` and has none — verified `metric-args.dto.ts:30`). `scope` is applied inside the repository via `orgScope()`, sourced only from `scopeFromVerifiedClaims`. So ADR-0001 §Decision-3 rung 6 — "the model has no `orgId` parameter to get wrong, and no prompt injection supplies one because the field does not exist in the tool definition" — is not an aspiration here; it is a property of the tool schema the model is handed. A prompt injection in the question can at most steer the model to a *different in-scope* `(function, args)` — a wrong-but-scoped query — which is visible via the `mapped:` tag (§2.3) and correctable by the user. That is ADR-0003's accepted residual, and it is the worst case.

**Finding check, as the prompt demanded:** there is **no** path in this design where the LLM's output becomes raw SQL, a free-form filter, or reaches the database outside the five functions. The design does not reopen the surface; it binds to the one ADR-0002 closed.

## Decision 2 — `intent` is derived server-side from the validated arguments, not set by the model and not inherent to the function.

The prompt asked whether each function inherently knows point-vs-slice, whether the model's arguments determine it, or both. The answer is precise and already partly built.

**The mechanism (verified in `usage-events.repository.ts`).** Each of the four metric functions computes `intent` from the *presence of `groupBy`* in the validated args: `groupBy` absent → `intent: 'point'` (a scalar `{ value, unit }`); `groupBy` present → `intent: 'slice'` (`{ groupBy, rows }`). See `getSpend` at lines 98–116: no branch reads a model-supplied `intent`, because there is none.

So, precisely:
- **Not inherent to the function.** `getSpend` returns either a point or a slice; the function does not "know" which — the same function serves both.
- **Not set by the model.** There is no `intent` input field. The model cannot assert an intent, correctly or otherwise. It can only choose *whether to include `groupBy`*.
- **Derived, server-side, deterministically.** The function owns the rule (`groupBy present ⇔ slice`); the model's validated arguments are the input to that rule. This is the "both" the prompt anticipated, resolved to a clean seam: the model influences intent only by supplying or omitting a `groupBy` that must first pass the Zod enum, and the server computes the discriminator.

**Why this is the right seam and not a formality.** The UI switches on `intent` and never infers (spec §1.8). If the model could *set* `intent`, a mis-set discriminator would mis-route the surface — an inline scalar rendered as a statement re-scope, or vice versa — and the failure would be silent. Because `intent` is computed from `groupBy` presence *after* validation, it cannot disagree with the data shape it labels. The trust boundary for the routing contract sits on the server, in the same function that runs the query, not in model output.

**`getStatement` is the render path, not a fifth tool — a real design decision.** When a metric function returns `intent: 'slice'` (say `getSpend` with `groupBy: 'model'`, `filter: { dimension: 'team', value: 'checkout' }`), the assistant has *answered*; the UI then *re-scopes the statement* (spec §1.8) by calling `getStatement` with that grouping and filter. `getStatement` is invoked deterministically by the UI, never chosen by the model. Exposing it as a fifth LLM tool would let the model return "the whole statement grouped by X" as an answer — redundant with the deterministic re-scope, and a larger, more ambiguous tool surface for no gain. Keeping the LLM tool set to four data tools + one control tool is the minimal surface that satisfies the contract. This mirrors ADR-0002 §3b's split — "the assistant *answers*, the screen *renders*, both over the same scoped SQL primitives."

## Decision 3 — The per-query $0.02 ceiling is enforced *before spend*, against a bounded worst-case, on a single model call. This is the centerpiece; the language matches the guarantee.

The prompt insisted on precision between enforce-before-spend and enforce-after-spend, because "hard cap" implies enforcement and the two are different guarantees. Here is the one being built, and why its language should match reality.

### 3a. One paid model call, not two — the design that makes the cap trivial to guarantee and removes a hallucination surface

ADR-0003 §4 sketched "capped output tokens, bounded input, ≤2 tool-call round-trips, the server tracks actual token usage and hard-stops." This ADR tightens that to **one** paid call:

- **Call 1 — mapping.** System prompt + five tool definitions + the user's question → the model returns exactly one `tool_use` (`tool_choice: "any"`, `max_tokens` small — it only has to emit a function name and a small args object). This is the *only* place the assistant spends money.
- **No synthesis call.** The structured `MetricResult` is rendered **deterministically** into the AnswerBlock — a server-side template over `(function, args, result)` produces the answer text ("checkout-service spend, last 7 days: **$1,284.50**"), and a `point` scalar renders inline while a `slice` re-scopes the statement (Decision 2). The LLM does the hard part — natural language → `(function, args)` — and nothing else.

**Why deterministic rendering over a second LLM synthesis call — argued, not assumed.** Two reasons, both material for a *ledger*:
1. **Exactness.** The product's entire claim is an accurate bill (ADR-0002 §1d chose integer micro-dollars for exactly this). Handing a figure to an LLM to phrase reintroduces the one thing a cost tool cannot ship: a hallucinated number. Deterministic templating renders the figure the query returned, verbatim.
2. **Cost.** It halves the paid round-trips (from ADR-0003's ≤2 to exactly 1) and removes the larger of the two calls (synthesis re-ingests the tool result). The accepted cost is that answers are templated, not conversational — which, for an itemized statement, is arguably the better product, not a compromise.

The ≤2-round-trip bound ADR-0003 wanted is now **structural, not a counter**: call 1 forces exactly one tool via `tool_choice: "any"`; there is no call 2 to forbid, because synthesis is deterministic. There is no loop to bound.

### 3b. Enforcement is before spend, because the cost of the one call is bounded a priori

The cost of call 1 is a function of inputs the server controls *before sending*:
- **Input tokens** = fixed system prompt + fixed five tool definitions + the user's question. The fixed prefix is a **known constant** (counted once). The only variable is the question, whose length the server bounds (reject/truncate questions over a fixed token budget *before* the call).
- **Output tokens** are capped a priori by `max_tokens` — the only upward-unbounded term, bounded by construction.

So the server computes a **worst-case cost before spending a cent**:

```
worstCase = (fixedPrefixTokens + maxQuestionTokens) × inputPrice
          + maxOutputTokens × outputPrice
```

and enforces `worstCase ≤ $0.02` as a pre-send gate. Because every term is fixed below the ceiling, **no admissible query can exceed the cap** — the cap is enforced by the token budget, before the model runs, not by metering actual spend and refusing mid-flight. That is the meaningful sense of "hard cap," and the language in the UI and docs should say *ceiling enforced by a bounded token budget*, not imply post-hoc metering.

**The one irreducible spend, named honestly.** You cannot know call 1's *actual* output tokens without making call 1. But its cost is bounded by `max_tokens` below the ceiling, so the assistant never makes an *unbounded* spend and never a *second* spend. There is exactly one bounded, sub-cap call — the accepted floor — and it is stated as such rather than hidden.

### 3c. The model, chosen to fit the cost envelope — itself a cost-cap decision

The task is narrow: map NL to one of four typed tools and supply small structured args. It does not need frontier reasoning, and the model choice is where the $0.02 budget is actually won or lost.

**Ship on `claude-haiku-4-5`** ($1 / 1M input, $5 / 1M output). This departs from the repo's usual "default to the most capable model" and the departure is deliberate: the cost cap is the centerpiece, and the model is the dominant cost term. Worst-case, uncached:

| Term | Bound | Cost |
|---|---|---|
| Fixed prefix (system + 5 tool defs) | ≤ 3,000 tok × $1/1M | $0.0030 |
| Question (capped) | ≤ 500 tok × $1/1M | $0.0005 |
| Output (one `tool_use`) | `max_tokens` 256 × $5/1M | $0.0013 |
| **Worst-case per query** | | **≈ $0.0048** |

≈ **$0.005 against a $0.02 ceiling — ~4× headroom**, before prompt-caching the fixed prefix (which drops input reads to ~0.1×). The same design on Opus 4.8 ($5/$25) would put a single call near $0.02 on input alone and blow the budget — so "which model" is not a footnote here, it is *part of* the cap design, and the defensible interview line is "I sized the model to the cost envelope; the task doesn't need Opus." Extended thinking is left off (Haiku 4.5 default) to keep output tokens predictable and the bound tight.

### 3d. What "query paused" actually is, and when the CostCapCard actually fires

Spec §2.3 says "query paused" and shows a `CostCapCard` on trigger. Under 3b, the trigger is a **pre-send refusal**: if `worstCase > $0.02` (in practice only when the question is pathologically long, since the prefix is fixed and small and `max_tokens` is small), the server refuses **before spending** and renders the `CostCapCard` ("Query paused — over the per-query cost cap") with a narrow-scope affordance. Zero dollars spent. That is genuinely "paused," not "answered then apologized for."

**The honest consequence, stated because the alternative is a false impression.** With Haiku, a fixed small prefix, a capped question, and small `max_tokens`, the worst-case sits ~4× under the ceiling *by design*. So in normal use the CostCapCard **effectively never fires** — which is the correct state for a well-designed hard cap, not a defect. The card is a wired, real backstop (it also covers a future model swap or config change that raises per-call cost); it is not a meter that trips during ordinary queries.

This directly shapes how `schedule-v2.md` §0 / §4 Jul 30 ("watch the $0.02 cost cap **actually trigger** — not 'the code path exists'") gets satisfied, and it is the [[feedback_manufacture_test_conditions_to_verify]] discipline applied on purpose: to *observe* the cap fire, manufacture the condition — temporarily lower the ceiling (e.g. to $0.003) or submit an over-length question — and watch the pre-send gate refuse. Demonstrating the guardrail means provoking it, and saying so plainly is the stronger interview answer than a meter theatrically ticking on every query.

### 3e. The client estimate is UX; the server budget is the boundary — ADR-0007's framing, and it applies

Spec §2.3: the ask bar shows "≈ $0.00X … client-side, UX only." This is the same shape as Atlas ADR-0007 §Decision-3: there, hiding a nav link / filtering the registry client-side is "attack-surface reduction and UX," and **the API role check is the real authorization backstop** — "I gate the load so the bundle isn't even requested, but I don't pretend a static bundle is a secret; the authorization boundary is the API." The framing transfers directly, and it does apply here:

- The **client estimate** is legibility — it sets the user's expectation as they type. A client that lies about, or deletes, its own estimate display changes nothing.
- The **server's pre-send worst-case budget** is the boundary — it recomputes from the actual request bytes and refuses before spending, exactly as ADR-0007's API recomputes the role on every data call regardless of what the client rendered.

So the interview line is ADR-0007's, transposed: *"I show the estimate so the cost is legible, but I don't pretend the client's number protects the bill — the server's bounded token budget is where the ceiling is enforced, before the call."* A check on the side the client controls is not the check.

## Decision 4 — Out-of-scope is a forced structured tool call, costs at most one bounded call, and cheap pre-checks catch only malformed input.

The prompt asked whether the system can know a query is out of scope *before* wasting a paid call, or whether detection necessarily costs money — and how that interacts with Decision 3.

**Semantic out-of-scope necessarily costs the one call — and that is correct.** Mapping natural language to a function *is* the model's job; a deterministic keyword pre-filter would be a worse re-implementation of exactly that, rejecting valid phrasings and admitting nonsense. So "is this answerable by one of the four functions?" is a model judgment, and its outcome is the result of **call 1**, not something knowable before it.

**The mechanism keeps that one call cheap and unambiguous.** With `tool_choice: "any"` over the four data tools **plus** `report_out_of_scope`, the model is forced to emit exactly one structured tool call and cannot ramble in prose (which would waste output tokens and be unparseable). If the question maps to a metric, it calls that tool; if not, it calls `report_out_of_scope({ reason, suggested_rephrasings })`, and the server renders the `OutOfScopeCard` (`role="status"`, `AlertTriangle`, `--warn-tint`, 2–3 `RephraseChip`s from `suggested_rephrasings`) — ADR-0003 §5's "deterministic out-of-scope fallback" made concrete. This is a `status`, not an `alert` (spec §2.3): an expected outcome, not an error.

**Interaction with Decision 3, made explicit.** An out-of-scope query is subject to the *same* pre-send budget as any other: it is one bounded call (`report_out_of_scope` output is tiny). So OOS is never free, but it is never more than one sub-cap call, and it needs no special cost handling — the pre-send gate already bounds it. There is exactly one legitimate **cheap pre-check that runs before spending**: malformed/oversized input — a question over the token budget is refused pre-send (that is the CostCapCard path of 3d, a bound-enforcement, not scope detection). The split is clean: *malformed or oversized* input is caught before spend; *semantic* out-of-scope costs the one bounded call, because only the model can judge it.

## Alternatives rejected

- **Let the model generate SQL (or fill a SQL template), then validate/strip it.** Rejected — and the reason is ADR-0002 §3a's, not re-derived: naming functions instead of building a query-builder is precisely what closed the generated-SQL surface. Model-authored SQL reopens it in its worst form (raw text, not even structured args), turning the allow-list back into enumerate-the-bad statement-stripping — the block-list posture ADR-0003 spent its length rejecting. Function-calling with structured args keeps the property the whole feature depends on: the model emits arguments, the server owns the `(function, args) → parameterized query` mapping, and Zod checks the arguments trivially.
- **Enforce the cost cap client-side, server trusts the client's estimate.** Rejected the same way ADR-0007 rejected client-side-only role gating: a check the client can rewrite is not a check. The client estimate is legibility (Decision 3e); the server's pre-send worst-case budget, recomputed from the request, is the boundary. Trusting the client's number would move the ceiling onto the side the client controls.
- **A second LLM call to phrase the answer.** Rejected per Decision 3a — it reintroduces numeric hallucination into a ledger and doubles the paid round-trips. Deterministic templating over the structured result is exact and cheaper.
- **Build the hourly query-count throttle now, "since we're already in the cost-guardrail file."** Rejected. It is explicitly designed-not-built in the locked spec (§0 item 7: "the hourly throttle is explicitly designed-not-built, no exceptions") and in ADR-0003 §Designed-not-built. Naming this rejection matters because this is exactly the scope-creep this branch has caught itself doing under time pressure — the per-query ceiling closes the cost hole (one pathological query); the throttle is a *volume* control for multi-user abuse the MVP demo does not exercise, and shipping it now would be the buzzword-over-need error ADR-0002 Decision 1 warned against. The UI consequence is honored: no hourly meter, no "queries left this hour" banner anywhere (spec §0 item 7).

## Findings surfaced (not details — the branch's method is to close its own open questions in writing)

1. **`getStatement` cannot render a *filtered* slice — its signature has no `filter`.** Decision 2 re-scopes the statement on `intent: 'slice'` by calling `getStatement(scope, { window, groupBy })`. But a slice can carry a filter (e.g. "spend by model **for team checkout**"), and `StatementArgs` (verified `types.ts:42` and `metric-args.dto.ts:39`) is `{ window, groupBy }` with **no filter field**. As built, re-scoping such a slice would silently drop the filter, contradicting spec §1.8 ("re-scope the statement **to that filter**, show a … `ViewingFilterChip`"). **Recommended fix:** add an optional `filter` to `StatementArgs`/`statementArgsSchema` and to `getStatement`'s `WHERE` — one clause, reusing the exact `filter` shape and predicate the metric functions already apply (`usage-events.repository.ts:86`). Small, and it makes §1.8 actually hold rather than half-hold. Flagged here as a required extension to ADR-0002's `getStatement`, to be built in the Jul 25 session, not discovered mid-UI.

2. **The assistant path must bound the rows fed back into the answer, independent of window span.** The metric functions apply no `LIMIT` (correct for the Statement screen, which wants every group). But a `groupBy: 'time'` over a very wide window can produce many rows; on the assistant path those rows are serialized into the AnswerBlock/re-scope. For the cost bound of Decision 3 to hold cleanly and for the AnswerBlock to stay legible, the **dispatch layer caps the rows it renders** (e.g. top-N with an "and M more" note), rather than changing the repository functions. This is ADR-0003 §4's "aggregate-only result sets … with a `LIMIT`" applied at the assistant boundary. Recorded so it is a deliberate bound, not an omission.

## Consequences (on approval)

- **`apps/api` gains** an `assistant` module: the five tool definitions (four projected from `metricArgsSchema`, one `report_out_of_scope`), a single-call Anthropic client on `claude-haiku-4-5` with `tool_choice: "any"` and a small `max_tokens`, a hardcoded five-name dispatch map to `UsageEventsRepository`, the pre-send worst-case cost gate, deterministic answer templating, and the `MetricResult`/OOS/CostCap response envelopes ADR-0003 §6 named. `scope` comes from the same guard that scopes every other read (JWT for the browser caller).
- **`getStatement` grows an optional `filter`** (Finding 1) — a `statement_args` schema change and one `WHERE` clause. Recorded here so the deviation from ADR-0002's `getStatement` signature is visible, not discovered.
- **A new config surface:** `ANTHROPIC_API_KEY` for the assistant. Per `schedule-v2.md` §8, verify Claude Code's own key does not shadow it and vice-versa; the assistant's key is server-side only, never shipped to the browser.
- **ADR numbering.** This is `0004`. Per ADR-0001/0002 §Consequences, `adr-nl-query-guardrails.md` is renamed `0003-nl-query-guardrails.md` in the build session that finally binds it — done alongside this ADR's implementation, not deferred further.
- **The résumé/LinkedIn line** `schedule-v2.md` §9 already lists — "cost-capping an AI feature inside a cost-monitoring product, the second-order-effects story" — now has its concrete spine: *enforced before spend, on a model sized to the envelope, with the guardrail visible on every answer.*

## Judgment calls surfaced rather than decided

- **Question-length cap value.** Decision 3 caps the question at a fixed token budget to make the worst-case near-constant. I recommend ~500 tokens (generous for a usage question, keeps worst-case ~4× under the ceiling). Say if you want it tighter (stricter cap, more headroom) or looser (longer questions, thinner margin) — the design holds either way; only the number moves.
- **Token counting for the pre-send gate.** The fixed prefix is counted once (a constant); the question can be measured by Anthropic's `count_tokens` (free, but one extra round-trip of latency) or by a conservative local estimate (chars ÷ ~3.5, over-counting so the bound never *under*-counts — fail-closed). I recommend the **local over-estimate**: no added latency, and over-estimation only makes the cap stricter, which is the safe direction for a cost gate. Say if you'd rather pay the round-trip for an exact count.

## Verification plan — reproduce, don't assert (mirrors ADR-0001/0002 §Verification)

1. **The allow-list holds by construction.** With a seeded org, drive the assistant with a normal question; confirm the executed query is one of the five functions with `scope` from the token, and that no request shape — including a question that *asks* for raw SQL or another org's data — produces anything but a scoped `(function, args)` call or an `OutOfScopeCard`. Log the dispatched `(name, args)` and confirm no SQL text ever originates from model output.
2. **Cross-tenant, through the model.** Authenticate as org B; ask the assistant, in natural language, for org A's spend by every phrasing available. Assert zero of A's data returns — the tool schema has no `orgId` to populate, so the model cannot express the request (ADR-0001 §Decision-3 rung 6, verified through the LLM caller).
3. **`intent` routes correctly and cannot be spoofed.** A point question renders inline; a slice question re-scopes the statement with the correct `ViewingFilterChip` — including a **filtered** slice, which exercises Finding 1's `getStatement` filter. Confirm the UI switched on the server's `intent`, never inferred it.
4. **The cap is enforced before spend — watched, not assumed.** Under production caps, confirm real queries cost ≈ $0.005 (`usage` from the response) against the $0.02 tag. Then **manufacture the trigger** ([[feedback_manufacture_test_conditions_to_verify]]): lower the ceiling to ~$0.003 (or submit an over-length question) and confirm the query is **refused before any spend** — CostCapCard shown, `usage` shows no call was made. Watching it fire is the milestone (`schedule-v2.md` §0 Jul 31 / §4 Jul 30), not the existence of the code path.
5. **Out-of-scope costs one bounded call and renders a status, not an error.** Ask something no function answers ("what's the weather"); confirm a single bounded call, a `report_out_of_scope` tool call, an `OutOfScopeCard` with `role="status"` and 2–3 `RephraseChip`s, and no second call.
6. **The mapped tag tells the truth.** Every answer shows `mapped: <function · dims · window>` matching the actually-dispatched call — the legibility that makes a mis-mapped (but in-scope) query visible and correctable, which is ADR-0003's accepted residual made auditable.

**Any of 1–5 failing is a finding reported as a finding, not worked around.**

## Amendment (2026-07-23) — Decision 3 was built on a paid-hosted-API premise this project does not hold; the guardrail is re-derived as a local compute budget, and the model moves to Ollama

**Status of what this amends:** the body above is left intact as the record of what was believed on 2026-07-23 when the ADR was proposed and the `assistant` module was first written against it. This amendment lands the same day, before that code is committed (`apps/api/src/assistant/**` is still untracked; `@anthropic-ai/sdk` is an uncommitted `package.json` change). It is written as a dated amendment, not a silent rewrite of Decision 3, on the same principle Decision 2 and Atlas ADR-0004's amendments follow: name the gap between what was believed and what is true, don't quietly patch the earlier text so the mistake disappears from the record.

### 0. The premise that broke, stated plainly

Decision 3 — the centerpiece — is built end to end on one premise: **each model call has a knowable per-token dollar cost to bound against.** Every concrete thing in 3b/3c/3d follows from it: the `worstCase = tokens × price ≤ $0.02` pre-send math, the $0.02 ceiling itself, the worked Haiku table, and the "Haiku over Opus *on cost grounds*" model choice. The premise is now known to be wrong for this project — not because the feature changed, but because a standing constraint was missing from the original brief: **no paid APIs, no subscriptions, no billing accounts, anywhere in this project — no exceptions.** That is my (the author's) omission from the brief, not a new requirement introduced late; the ADR should have been derived under it from the start.

A local model has **no per-token dollar cost**. So the price multiplier in every formula above goes to zero, and with it the literal meaning of "$0.02 cap," "≈ $0.005 per query," and "Haiku is cheaper than Opus." Those numbers do not survive. What has to be re-derived is exactly one question — *what is being bounded, and by what number* — and nothing else. Per the correction brief and on inspection, three things are **not** reopened and are carried forward untouched (see §4): the single-call architecture (3a), the enforce-*before* timing (3b's ordering), and the allow-list-by-construction dispatch (Decision 1). Only the substance of "what the ceiling measures" changes.

### 1. Why local, and why not the two tempting escape hatches

This is not a per-feature cost judgment; it is the project-wide rule applied. Two alternatives deserve an explicit, recorded rejection:

- **"Keep Anthropic just for this one feature — it's only ~$0.005 a query, the cap even proves it's cheap."** Rejected. The constraint is not "this feature is too expensive"; it is a standing rule with no per-feature exception, and the cheapness of *this* call is beside the point. The precedent is already set in the sibling repo: **Atlas's `ai-assistant` was originally built against a real Anthropic call, the cost concern was raised, and it was rebuilt against a local Ollama daemon** (`atlas/packages/api/src/app/ai-assistant/ollama-summary-client.ts`, whose header records the same reasoning — "no API key, no billing account, no per-request cost"). Cogent inherits that decision rather than relitigating it.
- **A hosted-but-"free-tier" LLM with function-calling (Gemini, Groq, Mistral free tiers).** Named because it superficially satisfies "no cost," and rejected on skepticism the correction brief asked for. Every one of these still requires a **billing-capable account and a server-side API key**, is **rate-limited** (a free tier is free-*until*-a-limit, not free), can flip to paid or change terms unilaterally, and introduces a network dependency a local demo cannot guarantee offline. "Permanently, unconditionally free with no account" is not what any of them offer; "free until you hit a wall or they change the deal" is. Local Ollama is $0, key-less, account-less, offline-capable, and already installed and running on this machine — it is the only option that satisfies the rule *by construction* rather than *until a limit*. The `MetricResult`/dispatch layer stays provider-agnostic (§4), so if a genuinely-free hosted tool-caller ever appears, swapping to it is a one-file change — but it is not the default, and the ADR does not pretend a free tier is equivalent to no account.

### 2. The real technical question the swap forces: does the local model do function-calling well enough — and what does the answer cost the design?

The hosted premise gave one thing for free that a local model does **not**: reliable, forced, structured tool output. Decisions 1/3/4 leaned on `tool_choice: { type: 'any' }` to guarantee "exactly one `tool_use` block, no prose," and repeatedly called the fallback branches (missing tool_use, unknown name, malformed args) *"structurally unreachable."* That guarantee has to be re-examined against Ollama, not assumed to transfer. Researched this session (sources below), three findings:

1. **Ollama supports tool-calling, and `llama3.2` carries the `tools` capability.** Both the 1B and 3B variants are tagged `tools`; Ollama's own model page says the 3B "excels at tool use." The response returns `message.tool_calls[]` as `{ function: { name, arguments } }` — a clean structured shape to dispatch on. So the *mechanism* exists locally.
2. **Forcing a tool call is NOT reliably available on the local path.** Ollama's tool-support blog lists *"Tool choice: force a model to use a tool"* under **Future improvements** for the native `/api/chat` endpoint — i.e. the native API does **not** guarantee the model emits a tool call rather than prose. The OpenAI-compatibility endpoint (`/v1/chat/completions`) is reported to accept `tool_choice`, but the support is soft-documented and version-dependent. **The honest design position: do not architecturally depend on forced tool choice.** Treat "the model returned prose, or no tool call, or malformed arguments" as a **reachable, expected** outcome, not an unreachable anomaly.
3. **`llama3.2` is a 3B model; its tool-calling reliability across a five-tool menu is materially below a hosted frontier model's,** and no source gives a hard benchmark to claim otherwise. It is adequate to *start* (installed, verified working for Atlas's free-text path) but its ability to consistently pick the right one of five tools and emit well-formed args is exactly the thing that must be *verified, not asserted*.

**The consequence for the dispatch design — and it is a real one, not cosmetic.** The defensive branches in `assistant.service.ts` — `if (!toolUse) → out-of-scope`, unknown-name `→ out-of-scope`, `metricArgsSchema.safeParse` failure `→ out-of-scope` — were written as belt-and-suspenders for a path the ADR body called unreachable. **With a local model they become the belt.** They are now the *expected* handling for a 3B model that emits prose, hallucinates a sixth tool name, or produces args that miss `window`. The good news, and the reason no code in that dispatch changes: **the module was already written to treat every one of these as out-of-scope rather than throw** (lines 94–121) — so the defensive parsing a hosted model made optional, and a local model makes mandatory, is already present. What changes is only the ADR's *characterization* of it: from "unreachable safety net" to "the primary robustness mechanism for a less-reliable local tool-caller." The allow-list property is untouched (the server still owns `(name, args) → parameterized query`; the model still has no `orgId` field to populate); only the *frequency* with which the reject-paths fire goes from ~never to occasionally, which is precisely why they must exist and be tested against real local output.

**Model decision — measured, not asserted, closed by a post-implementation re-run, not the first optimistic number.** Before writing any implementation code, `llama3.2:3B` was driven against the real 5-tool menu on this machine via a pre-implementation scratchpad measurement: 8 representative questions (point, slice, filtered-slice, one deliberately ambiguous, two out-of-scope) × 3 runs each = 24 live calls. A naive strict pass/fail on full argument validity read **2/24 (8.3%)** — but that hid two properties that failed for entirely different reasons:

1. **Tool selection: 24/24 (100%).** Every question — including the ambiguous one and both out-of-scope ones — produced a call to the correct tool. No hallucinated tool name; no five-tool menu silently narrowed to two or three. This is precisely the failure mode named as the actual trigger for switching to `qwen2.5:7b`, and across every measurement pass run this session (72 live calls total, below), it never once occurred.
2. **Argument shape: a real defect, first characterized as narrow, then found to be plural.** A follow-up n=9 diagnostic with an anchor date added showed correct dates in all 9 runs, but the object was serialized back as a *string* 8/9 times. A repair layer (`coerce-args.ts`, §6) was built for exactly that shape and the code implemented — at which point the discipline this session was built on (do not stop at the first number that looks like a fix) forced a **full 24-call re-run against the real, implemented dispatch pipeline**, not just a re-run of the narrow diagnostic that produced the original fix.

**That re-run is where the real story is — three rounds, not one, each closing a distinct, separately-diagnosed defect:**

| Round | Fix in place | Result | New defect found |
|---|---|---|---|
| 1 | String-repair only (`coerceStringifiedArgs`) | **13/24 (54.2%)** | Model omits `window` wrapper, flattens `from`/`to` to top level |
| 2 | + `liftFlattenedWindow` | **15/24 (62.5%)** | Model emits explicit `null` for omitted `groupBy`/`filter` (Zod `.optional()` ≠ accepts `null`); separately, zero-width windows for "today" questions |
| 3 | + `stripNullOptionalFields` + two new system-prompt worked examples (single-day window anchor, groupBy-vs-filter distinction) | **22/24 (91.7%)** | — |

Each round's failures were traced to raw model output and an exact Zod error before writing the next fix — not guessed at from the aggregate percentage (`scripts/verify-ollama-tool-calling.ts`, §6, is the re-runnable form of every one of these passes). The two remaining failures in the closing run are both understood and both already degrade gracefully through the existing dispatch fallthrough, not a crash or a wrong answer: one residual argument-shape flake on a repeat of the "today" phrasing (the fix reduced but did not eliminate this specific case's failure rate), and one case of the model declining to call any tool at all (`no_tool_call`, handled identically to an out-of-scope question per §2's design). Neither is a tool-hallucination or narrowed-tool-set case.

**Decision: ship on `llama3.2:3B`.** Across all three measurement rounds this session (72 live calls total), the pre-agreed switch trigger — tool hallucination or a narrowed effective tool set — never occurred once. Every defect found was an argument-shape or prompt-comprehension issue, and every one had a bounded, evidence-backed fix that was built, then re-verified, not assumed. `qwen2.5:7b` remains the documented fallback (§2) if a future model change or expanded question set finds a defect class this repair layer and prompt genuinely cannot address — but nothing measured this session argues for making that swap now.

**The 13-day "last week" finding, carried from the first measurement pass, is now closed and verified, not carried forward as open.** The `checkLastWeekSpan` check built into `scripts/verify-ollama-tool-calling.ts` specifically to re-verify this (§7 item 7) shows `lastWeekSpanDays: 7` on every one of the 6 relevant runs in the closing round — the sharper worked example fixed it.

### 3. The re-derived bound — a local compute budget, with real numbers and the same rigor as the Haiku table

**The framing, argued.** The correction brief offered two framings and invited a third. The one adopted is **Framing 1 (a resource/compute budget), with the dollar mapping preserved as explicit narrative but never as a displayed number** — which is the honest synthesis, and it rejects Framing 2's "keep a nominal dollar UI framing" as the *primary*, because a dollar sign on a number that is not money is exactly the false impression the brief (rightly) forbids. The guardrail's **spirit is unchanged**: a hard per-query ceiling, enforced before the system does the expensive thing, protecting one shared local resource from a single pathological query. What it **measures** changes from dollars to **tokens (a priori) and wall-clock inference time (the backstop)** — and this is not an invention, it lands directly on the load-bearing fact Atlas already discovered and tuned against: *a single local Ollama daemon runs one model instance and processes requests **serially**, on CPU, no GPU offload on this machine* (`ollama-summary-client.ts:27–56`). Serial CPU inference time is the scarce resource here, the way dollars were the scarce resource on a metered API.

**The bound has two parts, and the "before vs. after" distinction survives cleanly on the first:**

- **(a) Pre-compute admission gate — the true analogue of the old pre-send dollar gate, enforced *before* the daemon is touched.** Input size is fully known a priori: fixed prefix (system prompt + five tool definitions, counted once) + the user's question, length-capped. These token counts are **provider-independent** — a token budget is the same number whether or not anyone charges for it — so the *token* half of the old worst-case math survives the swap verbatim; only the `× price` multiplier vanishes. Concrete bound, unchanged in tokens from the original table:

  | Term | Bound |
  |---|---|
  | Fixed prefix (system + 5 tool defs) | ≤ ~3,000 tok (`FIXED_PREFIX_TOKENS`, computed from the real strings) |
  | Question (capped) | ≤ 500 tok (`MAX_QUESTION_TOKENS`) |
  | **Max admitted input** | **≤ ~3,500 tok** |
  | Output cap | 256 tok (`num_predict`, Ollama's max-output option — the local equivalent of `max_tokens`) |

  A question over the 500-token budget is **refused before the model runs** — zero compute spent — exactly the "genuinely paused, not answered-then-apologized" property of old §3d, transposed from dollars to compute. This is where "enforce before, not after" still holds literally.

- **(b) Wall-clock timeout backstop — for the one thing that is *not* knowable a priori locally.** You cannot know a call's actual inference *time* without running it, the same way old §3b admitted you cannot know actual output tokens without making the call. So the honest irreducible is bounded, not eliminated: a hard `AbortSignal.timeout` on the call (plus `num_predict` capping generation length) is the ceiling on the unknowable term. Per the "measure first, then set" decision, the constant below comes from real observed wall-time on this machine, not an anchored guess — two measurement passes, 32 warm-state calls total, plus one cold-start observation:

  **Warm-state latency (model already resident in memory) — the number that governs an interactive query in normal operation.** 32 real single-query calls on `llama3.2:3B`, concurrency 1, across both the reliability pass (23 warm calls, one excluded as the cold-start outlier) and the anchor-date diagnostic (9 calls, `keep_alive` held): **observed range 3.5 s to 20.2 s**, with longer-output calls (out-of-scope responses generating a reason + rephrasings) consistently at the top of that range and short metric-tool calls at the bottom. **Committed timeout: 45 s** — roughly 2.2× the observed 20.2 s warm-state worst case, the same headroom discipline the original ADR applied to its dollar cap (§3c's "~4× headroom" was the model for margin-sizing; 2× is proposed here in flag for confirmation, tighter than the dollar precedent because CPU-inference latency has less concurrency-driven upside variance than a token count does).

  **Cold-start latency (model not yet loaded, or unloaded by Ollama's idle timeout) — a separate, real fact that must not be silently folded into the interactive number, and reproduced twice, not a one-off.** The very first call in the original reliability pass — before the model had ever been loaded — took **74.1 s**. The pattern reproduced independently in the closing post-implementation gate run: that script's very first call (a fresh process, `keep_alive` set from the first request but nothing warmed beforehand) took **72.0 s** — a second, separate confirmation this is a real, repeatable daemon characteristic, not a fluke of one measurement. Ollama's default `keep_alive` unloads an idle model after 5 minutes, so any query after 5+ minutes of assistant inactivity pays this same tax again. A 45 s interactive timeout would have **killed both of those real requests.** This is not treated as noise or smoothed into a single bigger number — a single timeout covering both states would either be too tight for cold-start (frequent, confusing false budget-exceeded triggers) or too loose for warm-state (defeats the point of a tight compute backstop). **Mitigation, implemented and its effectiveness verified in isolation, though the standalone verification *scripts* deliberately do not exercise it (§6):** the assistant sends an explicit `keep_alive` (`30m`, confirmed effective in an earlier diagnostic — `keep_alive: '10m'` kept the model resident across 9 follow-up calls) on every request, **and** `OllamaAssistantClient.onModuleInit` issues one warm-up call to Ollama at API process boot. The standalone `verify-ollama-tool-calling.ts` script calls the daemon directly and does not go through `onModuleInit`, which is exactly why it (correctly) reproduces the cold-start cost on its own first call in both gate runs — that reproduction is evidence the mitigation is necessary, not evidence it doesn't work; the mitigation itself only runs inside the real NestJS process. This distinction is worth being precise about rather than eliding: cold-start latency is now understood and reproduced, but a real end-to-end confirmation of the `onModuleInit` warm-up specifically (start the API fresh, hit `/v1/assistant/ask` immediately, confirm no cold-start delay) has not yet been run — carried into §7 as an open verification item, not assumed working by construction.

  **Warm-state latency in the closing gate run ran slightly higher than the original 3.5–20.2 s range — 9.3 s to 23.0 s across the 23 non-cold-start calls** — plausibly because the system prompt grew with each added worked example (§2), increasing the fixed input every call pays. Still comfortably under the 45 s timeout (~2× headroom, tighter than the original ~2.2× but not materially so), so the committed constant is not revised, but the trend (a longer prompt raising warm-state latency) is worth watching if further worked examples are added later.

  **Both numbers are empirically tuned, exactly like Atlas's 90 s, and are NOT universal constants.** Atlas's 90 s was measured under 3 concurrent serial requests head-of-line-blocking on one CPU daemon (`ollama-summary-client.ts:27–56`); Cogent's 45 s is concurrency-1 by design (a single ask-bar query), which is why it lands well under Atlas's number rather than needing to match it. Re-verify both the 45 s and 74 s figures if any of: **the model** (§2's `qwen2.5:7b` fallback would raise both), **concurrency** (overlapping queries reintroduce the head-of-line blocking Atlas measured), or **the hardware/GPU-offload configuration**, changes. Full raw timing data for both passes is preserved in the verification script's output (§6) rather than only summarized here, per the same "reproduce, don't assert" discipline as the rest of this ADR's verification plan.

**Post-hoc reporting gets *richer*, not poorer, from the swap.** Old §3e reported real dollar spend from the hosted `usage` block. Ollama's response carries `prompt_eval_count` / `eval_count` (real token counts) **and** `prompt_eval_duration` / `eval_duration` / `total_duration` (real nanosecond timings). So the "actual cost, reported alongside the answer" affordance becomes "actual **tokens + actual wall-time**, both measured" — a more honest and more informative meter than a single dollar figure, and one that reports the thing actually being spent locally.

**The dollar story, kept honest as an interview artifact.** The résumé/LinkedIn line (`schedule-v2.md` §9, "cost-capping an AI feature inside a cost-monitoring product") is preserved — but as *narrative that names the mapping*, never as a fake UI number: *"The scarce resource in a hosted deploy is dollars; locally it's serial-inference wall-time on one CPU daemon. I sized the local budget with the same discipline — a pre-compute admission gate plus a tuned timeout — and I can show what it maps to in production: on Haiku 4.5 this call is ~$0.005 against a $0.02 ceiling, ~4× headroom. I metered the thing that's actually scarce where the code actually runs, rather than printing a dollar sign on a number that isn't money."* That keeps the full second-order-effects story and is *true*, which the alternative (a dollar meter over a $0 local call) is not.

### 4. What is explicitly NOT re-argued (carried forward from the body, untouched)

Per the correction brief, and confirmed on re-inspection, the swap does not disturb these — they are provider-independent and remain correct:

- **Single paid/compute call, no synthesis call (3a).** Still exactly one model call; the answer is still rendered by the deterministic server-side template (`answer-template.ts`), not a second LLM call. This is *more* right locally, not less: handing a bill to a 3B model to phrase reintroduces hallucination risk that is, if anything, higher than Haiku's. Exactness over conversational polish stands.
- **Enforce-before ordering (3b).** The admission gate (§3a above) runs before the daemon is touched. Only the quantity being gated changed (tokens/compute, not dollars); the ordering guarantee is intact.
- **Allow-list-by-construction dispatch (Decision 1).** The five-name hardcoded map, `scope` from the verified credential never from model input, and Zod re-validation of every args object are all unchanged. The model still has no `orgId` field to populate. §2 above *strengthens* the case for these branches (they now fire in normal operation), it does not weaken them.
- **`intent` derived server-side (Decision 2), and the `getStatement` filter finding (Finding 1).** Untouched — both are properties of the repository layer and the routing contract, with no dependency on which model or provider produced the args.

### 7. Verification — what actually ran, not what was planned

Appended to the body's plan (items 1–3, 6 hold unchanged — they are provider-independent):

7. **Tool-calling reliability gate + timing measurement — CLOSED, not open.** Three full 24-call rounds were run against the real, implemented dispatch pipeline (`scripts/verify-ollama-tool-calling.ts`), each preceded by tracing the prior round's failures to raw model output and an exact Zod error, not guessing from the aggregate number: **54.2% → 62.5% → 91.7% (22/24)**, closing four separately-diagnosed defects (§2's table and §6). Across all three rounds plus the original pre-implementation pass — **72 live calls total this session** — the pre-agreed switch trigger (tool hallucination, or the five-tool menu narrowing to two or three) **never occurred once**. The two residual failures in the closing round are understood (one repeat argument-shape flake, one model-declines-to-call-any-tool case) and both already degrade gracefully through the existing out-of-scope fallthrough. `npm run verify:ollama-tool-calling` re-runs this gate on demand; re-run it, per this same discipline, if the model, the prompt, or `coerce-args.ts` changes again — a passing run today is not a permanent guarantee.
8. **The compute budget is enforced before compute — watched, not asserted.** `checkAdmission()`'s unit tests (`budget-gate.spec.ts`) manufacture the budget-exceeded state by lowering `maxQuestionTokens`, confirming the gate refuses before `OllamaAssistantClient.chat()` is ever called. Both residual failure shapes from item 7 were individually watched, not assumed benign: `no_tool_call` → `out_of_scope` is covered by an existing unit test; the more common post-repair `metricArgsSchema` failure had **no test coverage at all** until this verification pass found the gap and closed it (`assistant.service.spec.ts`, "degrades cleanly to out_of_scope when repaired args still fail metricArgsSchema") — both confirmed to return a clean typed envelope, never a throw or a raw error reaching the caller.
9. **The boot-time warm-up — genuinely end-to-end verified, not left as a unit-tested claim, and it found a real bug and a real design gap in the process.** Docker/Postgres brought up, migrations run, and the actual `npm run start:dev` process booted for real — not a script, not a Nest `TestingModule`. Two findings surfaced only because the real app was run, not simulated:
   - **A real bug:** `ASSISTANT_MAX_QUESTION_TOKENS=` in `.env` is a *defined empty string*, not `undefined` — `??` only falls back on null/undefined, so `Number('')` evaluated to `0` and silently blocked every single query as `budget_exceeded`. Neither the unit tests (which always pass an explicit override) nor the verification scripts (which call `AssistantService` methods directly, bypassing `ConfigService`) could have caught this — it only manifests when the real `.env` file is actually loaded by a real `ConfigService`. Fixed in `assistant.service.ts`: an override is now used only if defined *and* non-blank.
   - **A real design gap:** the first boot's warm-up (bare `"hi"`, no `tools`) completed in `+17300ms`, and a second boot with the model already resident dropped to `+2411ms` — confirming `keep_alive` works. But the first REAL interactive query after that "warm" boot still **timed out at 45 s and returned a genuine 503** — proving the fail-safe timeout works exactly as designed, and simultaneously proving the warm-up was incomplete: a bare-text prompt loads the model weights but does not warm whatever Ollama does once per session to serve tool-constrained decoding. This is very likely the true explanation for the `point-spend run 1` outliers (64–72 s) that recurred as "the first tool-enabled call" across *both* gate re-runs in item 7 — not generic cold-start, specifically tool-grammar cold-start. Fixed by sending the real `buildSystemPrompt()` + `ASSISTANT_TOOLS` in the warm-up call, not a bare prompt (`ollama-client.ts`). Re-verified end-to-end after the fix: the corrected warm-up took **42.7 s** at boot (confirming the cost is real and substantial), and the very next real interactive query — real signup, real cookie, real HTTP call to `/v1/assistant/ask` — completed in **13.5 s with a correct answer**, comfortably inside the 45 s budget. This is the closing confirmation for the one item flagged as genuinely open; it is no longer open.

**Closing statement, so this amendment stands on its own record rather than requiring the reader to reconstruct the arc:** `llama3.2:3B` ships as the model. Across 72 scripted verification calls plus a full real-app end-to-end pass, the pre-agreed switch-to-`qwen2.5:7b` trigger — tool hallucination or a narrowed effective tool set — never occurred once. Reliability against the real dispatch pipeline closed at **91.7% (22/24)** after four separately-diagnosed and separately-fixed defects (stringified args, a flattened schema violation, an explicit-null/optional-field mismatch, a groupBy-vs-filter prompt ambiguity), each traced to raw model output and an exact Zod error before its fix was written. The compute budget (45 s warm-state timeout, 500-token admission gate) and its own estimator (which under-counted every sample, including the empty string, until `verify-token-estimate.ts` caught it and `MESSAGE_OVERHEAD_TOKENS` fixed it) are both real-verified. The boot-time warm-up is real-verified end-to-end, including a bug and a design gap the real-app test found and this session fixed. Nothing in this amendment rests on an assumption that was left unchecked.
